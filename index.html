01 项目概述

1.1 一句话定位

NodeHarvest 面向 AI Agent 的 Skill 发现、沉淀与调度工具链。

围绕 AI Skill 生态，构建一套能力发现与调度的工具链。帮助用户高效发现、评估和调用各类 AI 可执行能力（Skill、插件、MCP、API），解决当前 AI 能力分散、缺乏统一入口和智能调度的问题。

1.2 分阶段定位

阶段 定位 说明
当前 · MVP Skill 发现、沉淀与调度工具链 以 Skill 为具体形态落地。扫描是顺手完成的基础设施，并非产品重点；优先复用并集成 HarnessKit 已成熟的扫描、识别与管理能力。NodeHarvest 集中投入 Skill 的沉淀（可管、可复用）和调用集成（Agent 动态匹配）。
后续 · 演进 AI 能力的统一发现与调度基础设施 从 Skill 扩展到全品类 AI 能力（插件、MCP、API），成为异构能力的统一入口和调度层。保持工具链的可扩展性，避免过早发散。

1.3 项目背景

开发者在日常工作中会跨平台使用多种 AI Agent（如 Claude、CodeBuddy、Coze 等），每个平台上安装了大量 Skill。这些 Skill 的调用记录散落在不同 Context 中，无法被有效提取和复用。当一个项目完成后，开发者无法系统性地回顾"在什么任务下调用了哪些 Skill、效果如何"，导致经验流失。

更深层的问题：当前 AI 能力（Skill、插件、MCP、API）高度分散，缺乏统一入口管理和智能调度机制。用户不知道自己有哪些能力可用、哪个能力最适合当前任务。NodeHarvest 从 Skill 切入，逐步构建统一的能力发现与调度层。

核心洞察 Skill 的本质是"AI 员工的入职手册"——它把现实世界的经验拆成大白话告诉 Agent。一个 Skill 只能专注于某个具体方面，过于宏观则失去指导意义。NodeHarvest 不创造 Skill，而是收割 Skill 使用过程中的经验节点，让能力可发现、可沉淀、可复用。

1.4 核心价值

价值点 说明
统一入口管理异构 AI 能力 Skill、插件、MCP、API 等不同类型的能力，通过一个工具统一发现和管理
提升能力发现与匹配效率 扫描本地已安装能力，辨别和评估可用性，支撑 Agent 的动态匹配决策
沉淀调用经验，实现跨项目复用 将工作过程中的 Skill 调用节点结构化为 Markdown，未来类似项目可直接复用
支撑后续调度决策 扫描结果直接支撑后续辨别与调度流程，为 Agent 智能调度提供数据基础

1.5 项目名称

名称 NodeHarvest
含义 收割节点（Node + Harvest）——从工作中收割关键上下文节点，沉淀为可复用知识
命名逻辑 务实、有画面感。"收割"呼应"沉淀"功能定位，"节点"对应能力调用中的关键时刻

1.6 已对齐原则

  1. 扫描是基础前置环节，覆盖所有可调用组件类型（Skill、插件、MCP、API），但不是产品重点——是顺手做的基础设施。
  2. 核心在沉淀与调度：Skill 的沉淀（可管、可复用）和调用集成（Agent 动态匹配）才是真正的价值所在。
  3. 扫描结果直接支撑后续流程：辨别 → 调度，不是独立功能而是链路的一环。
  4. MVP 聚焦核心链路：发现 → 沉淀 → 复用，避免过早发散到全品类能力管理。
  5. 保持工具链的可扩展性：当前以 Skill 为切入点，架构上预留向插件/MCP/API 扩展的空间。
  6. 四层模型收敛为三层：原“扫描 → 沉淀 → 使用 → 调用”中，“使用”与“调用”缺乏可执行的边界，现合并为“调用集成”，形成“扫描基础设施 → 沉淀与管理 → 调用集成”三层。
  7. 优先集成 HarnessKit，而非重复建设扫描层：在遵守 Apache-2.0 许可证及资源例外条款的前提下，复用其 Agent/扩展发现、跨平台适配、审计和 CLI 等适合的核心能力，把主要研发资源投入第二、第三层。

03 核心功能架构

原四层模型为“扫描 → 沉淀 → 使用 → 调用”。调研后确认，“使用”与“调用”当前没有稳定、可验证的产品边界，因此合并为调用集成。现阶段采用三层架构：第一层复用成熟基础设施，第二、第三层由 NodeHarvest 重点建设。

01

扫描基础设施 (Scan)

集成优先 非核心差异化

发现本地 Agent、Skill、MCP、Plugin、Hook 与 Agent-first CLI，并处理跨平台路径和格式差异。该层优先接入 HarnessKit 已成熟且许可证允许复用的核心能力，不重复投入完整扫描系统。

02

沉淀与管理 (Harvest)

MVP 核心能力

从工作 Context 中提取 Skill 调用节点、任务语义、调用方式与结果反馈，形成可索引、可评估、可版本化、可复用的经验资产。Markdown 是首个载体，但数据模型不局限于文档。

03

调用集成 (Invoke)

MVP 核心能力

面向 Agent 暴露可查询、可匹配、可调用的能力入口，根据当前任务和历史沉淀动态推荐或选择 Skill，并记录调用反馈，形成“匹配 → 调用 → 反馈 → 再沉淀”的闭环。

+

横向支撑能力

渐进建设

可视化管理、效果评估、GitHub 私有仓库同步与跨设备流转不再作为独立产品层，而是按需服务于沉淀层和调用层。

3.1 HarnessKit 集成决策

决策项共识
为什么接入HarnessKit 已将多 Agent、多扩展类型的发现、路径适配、原位管理、安全审计及 CLI/Web 入口做得较完整，继续自研同类扫描能力会稀释 NodeHarvest 在沉淀与调用集成上的投入。
功能范围产品决策是将 HarnessKit 的现有功能整体纳入 NodeHarvest 的扫描与能力管理基础设施，包括 Agent/扩展发现、路径与格式适配、扩展元数据、审计、CLI、Web 管理及其余可合法复用的功能。NodeHarvest 不在产品层重复讨论逐项取舍。
品牌与受限资源功能可以集成，但不等于复制上游品牌。HarnessKit 名称、Logo、商标以及明确排除在 Apache-2.0 之外的美术资源不直接复用。
工程实现授权库级复用、代码合并、CLI 调用、进程适配、版本固定与升级策略属于工程实现问题，由 AI/工程执行者依据可维护性、兼容性和许可证合规直接决策，不升级为产品未决问题。
许可证要求HarnessKit 代码采用 Apache-2.0，可在满足保留许可证与归属声明、标注修改等条件下使用、修改和分发；其 README 明确排除的美术资源不纳入复用范围。正式集成前还需核对上游 NOTICE、依赖许可证和具体文件头。
研发资源分配 扫描层做到“可靠可用、便于接入”即可。NodeHarvest 的主要研发与产品验证资源集中在第二层“沉淀与管理”和第三层“调用集成”，并用真实 Agent 工作流验证两层之间的反馈闭环。

3.3 沉淀文档结构（草案）

提取出的 Markdown 文档应包含以下要素，每份文档对应一个项目/任务的关键节点记录：

字段 必填 说明
项目/任务名称 是 用户在调用 Skill 时同时输入的任务描述
Skill 列表 是 本项目调用的所有 Skill（含主动和被动）
调用方式 是 主动调用（用户指定） / 被动调用（Agent 自动）
调用上下文 是 "在什么情况下调用了这个 Skill"
时间戳 否 后续管理模块可补充调用耗时
效果备注 否 后续管理模块可补充效果评估
设计原则 沉淀文档保持极简——十几行、几百字。不追求大而全的记录，只提取关键节点。目标是"一个很简单的 Markdown，但包含了所有 Skill 调用与任务上下文的关联"。

3.4 Skill Flow：核心展示与管理对象

NodeHarvest 不以“通关界面”、耗时排行榜或扫描列表作为核心展示，而是展示一条可回顾的 Skill Flow：把完成一项工作的关键任务节点，与其调用的 Skill 节点连接起来，形成经验路径。

节点类型展示内容管理价值
工作节点要完成什么任务、任务所处阶段、产生了什么结果还原工作的推进过程
Skill 节点在该任务下调用了什么 Skill、主动或被动、为什么调用建立任务与能力的关联
结果/经验节点是否解决问题、效果如何、有哪些可复用经验或注意事项支持复盘与下次匹配
核心输出 展示重点不是“用了多久”，而是“为了完成什么工作，在什么节点调用了什么 Skill，结果如何，留下了什么经验”。Skill Flow 既是可视化结构，也是后续检索、管理和 Agent 动态匹配的数据基础。

3.5 历史 Context 的整理方式

NodeHarvest 不要求实时监听或强制捕获 Agent 的每一次调用。对于已经结束的项目，开发者可以在原有 Context 中加载 NodeHarvest CLI 与配套 Skill，也可以导出完整聊天记录、日志或其他可访问材料，再交给工具分析。配套 Skill 负责告诉 Agent 如何识别并整理其中的工作节点、Skill 节点和经验节点。

  1. 输入由开发者决定。 可以使用当前 Context、历史对话、导出的完整聊天记录、Agent 日志或其他开发者能够取得的材料。
  2. 工具做尽力提取，不承诺恢复不存在的信息。 如果上下文曾被压缩、摘要中省略了 Skill 调用，且记忆或日志中也没有保留，NodeHarvest 不负责重建缺失事实。
  3. 不做强制侵入式采集。 不为追求“完整捕获”而深度侵入每个 Agent、强制常驻监听或制造额外复杂度。
  4. 开发者拥有自由组合权。 NodeHarvest 提供 CLI、数据结构和使用说明 Skill，不限制开发者如何取得、组合和分析输入。

04 技术决策与共识

以下为讨论中三方达成明确一致的关键决策点，作为开发基线约束。

  1. 形态：CLI 工具，非 GUI。 CLI 对 Agent 友好（命令式调用，无需精准控制鼠标事件），轻量化，开发周期短。面向开发者群体普遍熟悉 CLI 交互。暂不做图形界面。
  2. 定位：工具，非子 Agent。 NodeHarvest 是一个被 Agent 调用的工具（Tool），不独立接入 API。如果接入 API 则等同于独立 Agent，增加用户配置成本，偏离工具定位。
  3. Skill 配套：附带一份使用说明 Skill。 该 Skill 的作用是"告诉调用它的 Agent：这个工具是干什么用的、怎么用"。本质是一份教程/说明书。
  4. 分工模式：问题驱动，非角色驱动。 不按前端/后端/服务器拆分，而是"谁提出问题，谁就解决那个问题"。讲话人1 搭建基础基座，其余各自认领自己发现的问题。
  5. 开源策略：先开源，后考虑商业化。 当前阶段定位为效率工具，参考 Skill 社区模式——开源分享、社群交流、持续进步。不被长远的商业化困住。
  6. 存储方案：GitHub 私人仓库。 作为免费云存储实现跨设备同步。这是当前最简单的方案，未来可替换。
  7. 扫描层确定优先集成 HarnessKit。 HarnessKit 已覆盖多 Agent 与多扩展类型的发现、管理、审计和 CLI 能力。NodeHarvest 不再从零建设完整扫描系统，而是以适配器/模块方式复用适合的核心部分。
  8. 许可证合规是集成前置条件。 复用范围遵守 Apache-2.0 的许可证、归属和修改声明要求；不使用其明确排除在许可证之外的美术资源，并在落地前核对 NOTICE 与第三方依赖。
  9. 历史整理采用开发者驱动、尽力提取。 用户自行提供当前 Context、历史对话、导出记录或日志；工具负责分析已有材料，不承诺恢复被上下文压缩或源系统丢弃的信息。
  10. 不做强行完整捕获。 NodeHarvest 不常驻监控所有 Agent，也不为完整记录而侵入各平台运行时。它是可自由组合的开发者工具，不是强制接管工作流的系统。
  11. Skill 耗时不属于产品指标。 核心展示是工作节点、Skill 节点、结果与经验之间的关系，而不是单个 Skill 的读取或执行秒数。
  12. 产品决策与工程决策分离。 团队决定做什么、服务谁、提供什么价值；存在标准工程判断的问题由 AI/工程执行者依据约束直接落地，不进入产品未决清单。

5.1 交付物清单

5.2 概念辨析：Skill / 插件 / MCP / 应用

讨论中对这几个概念进行了澄清，以下为团队共识定义：

Skill技能

本质是"一份说明书 + 一些工具"。把具体怎么做某件事用清晰的大白话告诉 Agent。长度通常不超过千字，只专注于某一具体方面。相当于"AI 员工的入职手册"。

插件Plugin

Agent 平台的功能扩展，可以接入应用让智能体接管操作。面向 GUI 层的集成。

MCPModel Context Protocol

标准接入协议。所有兼容该协议的服务（无论是一个搜索工具还是一个自主 Agent）都可以接进来。本质是"拓展能力接入的标准接口"。

应用Application

Agent 平台中可接入的外部应用，让智能体接管操作。偏向业务系统集成。

关键认知对齐 NodeHarvest 不是 Skill、不是插件、不是 MCP、不是应用——它是一个CLI 工具。附带一份 Skill 作为使用说明。工具被 Agent 通过命令调用，返回结果。

06 团队分工模型

6.1 分工原则：问题驱动

本项目不采用传统的"前端/后端/服务器"三段式分工，而是采用"问题驱动分工"模式：每个人在讨论中提出的问题，就是他要解决的工作方向。提出问题 = 认领问题。

分工逻辑 同一个项目，不需要前端、后端、服务器的角色拆分。每个人基于自己的理解和视角发现问题，问题的提出者就是解决者。讲话人1 负责搭建最基础的基座，其余各自认领。

6.2 参与者画像与认领方向

S1
讲话人1 · 架构师 / 引导者
角色定位：基座搭建 + 概念对齐 + 收敛总结

负责搭建项目基础架构（CLI 基座 + Skill 框架）。在讨论中持续澄清概念（CLI vs GUI、Skill vs 插件 vs MCP、Agent 架构），引导讨论从发散到收敛。产出 PRD 和共识文档。

S2
讲话人2 · 务实派 / 验证者
角色定位：技术可行性验证 + 偏好反馈

发言精炼但直击要害。提出"不喜欢终端""CI 东西我不怎么用"等关键偏好反馈，验证设计方向。关注工具的实际使用体验和成熟度演进路径。

S3
讲话人3 · 产品视角 / UX 代言人
角色定位：用户场景 + 展示需求 + 体验设计

产品感最强的角色。从用户视角持续追问"怎么展示""怎么演示""怎么让用户看到效率提升"。提出"通关界面""调用耗时展示""项目对比图"等产品化方向。同时带来摄影/编导领域的真实 Skill 使用经验。

评估并接入 HarnessKit 的可复用核心能力；定义稳定的适配器边界；实现上下文节点提取、结构化沉淀、任务匹配与 Agent 调用反馈。附带使用说明 Skill。
阶段二 · 经验管理
Skill Flow 展示、检索与复用
围绕工作节点、Skill 节点、结果与经验建立可视化关系，支持按项目、任务和 Skill 检索，帮助开发者复盘“什么任务用了什么 Skill、效果如何”，并为后续动态匹配提供依据。
阶段三 · 演进 · 统一调度基础设施
全品类能力 + 跨设备同步 + 开源生态
从 Skill 扩展到插件/MCP/API 全品类能力管理。GitHub 仓库同步落地。开源发布，建立社群。定位演进为：AI 能力的统一发现与调度基础设施。
阶段说明 MVP 聚焦核心链路：发现 → 沉淀 → 复用。扫描是基础前置环节（顺手做的基础设施），核心是沉淀（可管、可复用）和调用集成（Agent 动态匹配）。阶段三从 Skill 扩展到全品类 AI 能力，演进为统一调度基础设施。

08 术语表

术语 全称 定义
CLI Command-Line Interface 命令行式交互。Agent 友好——只需知道命令即可调用，无需控制 GUI 鼠标事件。轻量化，开发周期短。
GUI Graphical User Interface 图形用户界面。触摸/鼠标交互。开发复杂，当前阶段不采用。
Skill — Agent 的"入职手册"。把现实世界经验拆成大白话告诉 Agent 怎么做某件事。专注单一领域，不超过千字。
Agent AI Agent 拥有工具调用能力 + LLM 推理能力的智能体。通过调用 Tool（函数/命令）执行任务并获取结果。
Sub-agent 子 Agent 主 Agent 调用的从属 Agent。复用主 Agent 的 API Key，Context 互不干扰。NodeHarvest 不是 Sub-agent。
Context 上下文 一次 Agent 对话的完整交互记录。Skill 调用记录散落在不同 Context 中。
节点 Node Skill Flow 的基本单元，包括工作节点、Skill 节点与结果/经验节点；通过节点关系还原任务如何借助 Skill 完成。
OPC One Person Company 超级个体 / 一人公司。NodeHarvest 的核心目标用户群体之一。
主动调用 Active Call 用户主动指定 Agent 使用某个 Skill（如通过"+"号附带）。
被动调用 Passive Call Agent 在执行任务过程中自动调用 Skill，用户未显式指定。

9.1 已确认，不再列为未决问题

事项结论
扫描结果怎么展示扫描展示不是核心产品问题；HarnessKit 的现有能力整体纳入基础设施。NodeHarvest 自身的核心展示对象是 Skill Flow。
“通关界面”不作为待决问题或 MVP 承诺。它仅保留为远期方向/分工灵感，不影响当前产品定义。
Skill 调用耗时不适合本项目核心价值，不纳入产品指标和路线图。
被动调用完整捕获不追求平台级完整捕获。开发者提供可访问的 Context、聊天导出或日志，NodeHarvest 尽力提取。
上下文被压缩属于输入信息边界。源材料未保留的事实无法恢复，工具不为此实施侵入式监控。
Skill 粒度属于通用 Skill 设计知识，与 NodeHarvest 当前产品范围无直接关系，从未决清单移除。
CLI 还是 Sub-agent已明确：NodeHarvest 是给 Agent 使用的 CLI 基础设施，并附带说明 Skill；不演进为独立 Sub-agent。
HarnessKit 如何工程集成产品上确定整体集成其合法可复用功能；具体技术路径由 AI/工程执行者决策。
GitHub 容量与频率属于工程约束验证，不是产品方向问题。按轻量文本经验库设计，并由实现阶段处理仓库健康、文件组织与异常提示。

9.2 当前真正的产品待决事项

P-01
Skill Flow 的最小经验模型
待验证

需要通过真实项目验证：工作节点、Skill 节点、结果/经验节点是否足以支持复盘与复用；“效果如何”采用自由文本、标签、状态还是多种方式组合。

判断标准：能否清晰回答“什么任务下调用了什么 Skill、为什么调用、工作如何完成、留下了什么经验”。
P-02
沉淀经验如何进入 Agent 的动态匹配
待验证

需要定义 Agent 查询历史经验时的最小输入与输出：当前任务如何描述，候选 Skill 如何排序，历史效果与经验如何参与推荐，以及调用后如何回写新的结果节点。

目标闭环：任务 → 匹配经验 → 推荐/调用 Skill → 记录结果 → 更新经验。
P-03
开源边界与项目差异化
待讨论

在整体开源方向下，仍需确定 NodeHarvest 自研的 Skill Flow 数据规范、经验匹配逻辑、调用闭环与社区资产如何形成明确差异化，以及各模块的发布边界。
