# NodeHarvest 三人协作与另外两位成员贡献指南

> 更新日期：2026-07-26
> 适用阶段：可靠 Scan 收尾 → 最小 Skill Flow → 动态匹配闭环

## 这份说明写给谁

NodeHarvest 由**三个人**共同推进：产品负责人，以及会议记录中的另外两位成员。

这份文档不重新定义整个团队，也不把项目误写成“双人项目”。它只回答一个问题：**在产品负责人持续维护方向、共识和产品决策的前提下，另外两位成员怎样以各自擅长的方式，为当前 NodeHarvest 做出可验证的贡献。**

会议记录用于理解两位成员的观察方式、表达偏好和真实经验；如果会议中的早期想法与当前共识首页不一致，**一律以最新共识首页为准**。因此，终端偏好、通关界面、调用耗时、项目对比等早期意见可以作为发现问题的线索，但不能覆盖已经确认的 CLI 形态、Skill Flow 核心对象和 Scan → Harvest → Invoke 产品主线。

## 三人如何共同工作

三人团队继续采用最新共识确定的**问题驱动协作**，而不是固定的前端、后端或服务器分工：

- **产品负责人**维护产品定位、目标用户、功能边界、优先级与最终产品决策；
- **另外两位成员**从真实使用和真实项目场景中发现问题，提出证据，认领可交付工作并完成验证；
- **工程执行者**对工程、安全、合规、测试、可靠性、性能、兼容性和维护等有标准答案的问题直接处理，不把执行责任转回产品负责人；
- 一项工作设置一位负责人和一位复核人，产品负责人不需要成为每项工程工作的审批节点。

## 共同遵守的最新产品基线

1. NodeHarvest 是供 Agent 调用的 CLI 工具，并附带使用说明 Skill；不是 GUI，也不是独立 Agent。
2. 当前产品链路是 **Scan → Harvest → Invoke**。
3. Scan 是可靠基础设施，不是主要差异化；主要用户价值在经验沉淀、复用和动态匹配。
4. HarnessKit 的合法可复用能力优先集成，不重复建设同类扫描系统。
5. 历史整理由开发者提供 Context、聊天导出或日志，NodeHarvest 尽力提取，不承诺恢复源材料中不存在的信息。
6. 不通过强制常驻监听或侵入各 Agent 运行时追求完整捕获。
7. 核心展示与管理对象是 Skill Flow：工作节点、Skill 节点、结果/经验节点及其关系。
8. Skill 调用耗时、通关界面和扫描列表不是当前核心产品指标或 MVP 承诺。
9. 工程、安全、合规及非功能问题直接解决；只有真实产品冲突才提交产品负责人决策。

## 成员二：务实的流程验证者

### 会议画像带来的优势

这位成员表达精炼，重视工具是否真的能用，也会直接指出“不喜欢终端”“不熟悉 CI”等实际阻力。这些反馈不用于重新讨论 NodeHarvest 是否应做 CLI——该产品形态已有共识；它们最有价值的用途，是帮助团队识别：**一个不愿研究工具内部机制的开发者，能否在 Agent 协助下顺利完成安装、诊断、扫描、故障恢复和历史整理。**

### 当前应承担的贡献

1. **验证首次使用路径**
   在真实环境中完成安装、诊断和扫描，记录哪些步骤必须依赖额外解释、哪些提示无法直接行动、哪些结果难以理解。

2. **验证故障体验**
   覆盖断网、provider 不可用、旧快照、损坏版本和回滚场景，确认用户始终能知道结果是最新、过期还是不可用，并能理解下一步该做什么。

3. **验证 Agent 友好性**
   不要求本人偏好终端，而是观察 Agent 能否通过稳定命令和结构化输出正确调用 NodeHarvest，用户是否只需表达目标即可获得结果。

4. **控制使用成本**
   记录为了完成一次扫描或历史整理，用户需要提供多少信息、修正多少次、查阅多少说明。把“太麻烦”转化为可复现步骤和明确验收条件。

5. **复核成熟度声明**
   对尚未在真实平台验证的能力保持谨慎，防止把资产解析支持误写成完整平台可用，也防止把旧数据或模拟结果描述为真实新结果。

### 当前交付物

- 一份首次使用记录：目标、步骤、结果、阻力和可行动建议；
- 一组故障场景验收结果：正常、断网、provider 不可用、旧快照、损坏与回滚；
- 一份 CLI/Agent 调用体验问题清单，每项包含复现方式和完成标准；
- 至少一个已结束开发项目的可脱敏 Context 或聊天导出，用于 Harvest 验证。

### 完成标准

> 一个不了解 NodeHarvest 内部机制的开发者，可以让 Agent 完成诊断和扫描；发生故障时，能够理解结果可信度，并知道下一步如何恢复。

## 成员三：真实场景与 Skill Flow 验证者

### 会议画像带来的优势

这位成员持续从用户视角追问“怎么展示”“怎么演示”“怎样让用户看到价值”，并带有摄影、编导等真实 Skill 使用经验。会议中的“通关界面”“耗时展示”“项目对比图”不是当前产品承诺，但这些提问背后的能力仍然重要：**把抽象的数据模型放进真实工作过程，判断用户是否看得懂、是否愿意复用、是否能据此做下一次选择。**

### 当前应承担的贡献

1. **提供真实结束项目样本**
   从摄影、编导或其他已经完成的项目中，准备脱敏后的 Context、聊天记录或日志。样本应包含明确任务、实际 Skill 调用和可观察结果，而不是为模型临时编造的演示数据。

2. **验证最小 Skill Flow**
   用真实材料检查工作节点、Skill 节点和结果/经验节点是否足以还原“做了什么、用了什么、为什么使用、工作如何完成、留下什么经验”。

3. **定义极简经验表达**
   与产品负责人共同验证十几行、几百字的 Markdown 是否已经足够。重点记录必要字段、缺失信息、置信度和人工修订，不把文档扩张为全量日志。

4. **验证复盘与复用价值**
   让没有参与原项目的人阅读 Skill Flow，检查其能否理解关键路径，并在相似任务中找到可采用的 Skill 和注意事项。

5. **验证推荐理由**
   进入 Invoke 阶段后，检查候选 Skill 的推荐理由是否引用了真实历史效果，能否帮助 Agent 或用户做选择，而不是只返回一个能力列表。

### 当前交付物

- 1–2 个脱敏后的真实项目样本；
- 每个样本对应的一份极简 Skill Flow Markdown；
- 人工修订记录：缺了什么、改了什么、为什么改、修订成本多高；
- 对 P-01 最小经验模型的验证结论；
- 进入 Invoke 阶段后，对推荐理由和历史证据可理解性的验证记录。

### 完成标准

> 不熟悉原项目的人阅读 Skill Flow 后，能够准确说明任务如何推进、调用了什么 Skill、为什么调用、结果怎样，以及哪些经验值得在下一次任务中复用。

## 两位成员如何配合

两位成员不是分别承担“技术”和“产品”后各自交付结论，而是围绕同一个用户闭环相互复核：

| 批次 | 成员二重点 | 成员三重点 | 共同完成信号 |
|---|---|---|---|
| Scan 可靠收尾 | 验证安装、诊断、失败、旧快照和回滚体验 | 检查状态说明能否被非实现者理解 | 用户知道结果是否可信，也知道如何恢复 |
| 最小 Skill Flow | 提供开发流程样本，记录整理与修订成本 | 提供真实场景样本，验证节点与经验表达 | 低成本回答任务、Skill、原因、结果和经验 |
| Invoke 动态匹配 | 验证查询和调用是否顺畅、结果是否可行动 | 验证推荐理由与历史证据是否可信 | 完成任务 → 推荐 → 使用 → 结果 → 新经验闭环 |

默认由发现问题的人担任负责人，另一位成员担任复核人；如果问题涉及产品定位、功能范围或真实体验取舍，再提交产品负责人判断。

## 一项贡献如何进入项目

### 1. 把意见改写成问题

每项工作至少写清：

- 用户在什么场景遇到问题；
- 当前行为和证据是什么；
- 期望的用户结果是什么；
- 如何复现或提供样本；
- 怎样才算完成。

“我不喜欢”“看起来不好用”“应该做个界面”都不是可执行工作项。需要继续追问其背后的真实阻力，并转化为可验证问题。

### 2. 认领并交付最小批次

- 发现者优先认领；
- 一项工作只设一位负责人；
- 大问题拆成可以独立验证的小批次；
- 重要样本先脱敏，禁止提交原始私密 Context、密钥或个人数据；
- 结论、证据、限制和验证结果进入项目仓库与 Asana，不只保留在聊天里。

### 3. 相互复核

复核时重点检查：

1. 是否符合最新共识，而不是恢复会议中的早期设想；
2. 是否产生用户可感知的结果；
3. 是否有真实样本或可复现证据；
4. 是否把旧数据、模拟结果或未验证平台描述成已完成；
5. 是否存在隐私、许可证或供应链风险；
6. 失败后用户是否知道状态和下一步。

### 4. 同步状态

- Asana 用于任务认领、执行状态、交接和验收证据；
- 代码、数据规范、研究和验证材料进入组织仓库；
- 面向用户的能力变化同步到公开产品状态页；
- 未达到验收条件时保持“执行中”或“待验证”，不能提前标记完成。

## 交接模板

```markdown

用户现在可以……

## 使用场景或样本
- ……

## 验证证据

- 真实使用：……

## 已知限制
- ……

## 请重点复核
- ……
```

## 何时才需要产品负责人决策

只有以下情况暂停执行并提交产品负责人：

- 要改变 NodeHarvest 的定位、目标用户或 CLI 产品形态；
- 要新增或删除一项用户功能，且会改变 MVP 范围；
- 两种方案代表明显不同的用户价值、体验或优先级；
- 真实项目样本推翻 P-01 或 P-02 的核心产品假设；
- 要改变已确认的开源方向或作出不可逆生态承诺。

工程架构、安全、合规、测试、可靠性、性能、兼容性、错误处理、文档、发布和内部重构等事项，由执行者采用标准方案直接处理、验证和记录。当前没有需要产品负责人立即决策的问题。
