# NodeHarvest 双人贡献协作指南

> 更新日期：2026-07-26<br>
> 适用阶段：可靠 Scan → 最小 Skill Flow → 动态匹配闭环

## 协作目标

NodeHarvest 当前由两位成员共同推进。项目不按“前端 / 后端”或固定职位切割，而采用共识首页确定的**问题驱动协作**：谁发现并说明一个真实问题，谁优先认领并推动它得到验证。

双人协作的重点不是让两个人同时修改同一处代码，而是让每个产品批次都同时具备：

- 明确的用户结果；
- 可复核的实现；
- 真实使用反馈；
- 完整的研究、决策与验证记录。

## 共同遵守的产品基线

1. NodeHarvest 是供 Agent 调用的 CLI 工具，不是 GUI，也不是独立 Agent。
2. 产品链路为 **Scan → Harvest → Invoke**。
3. Scan 是可靠基础设施；主要产品价值在 Skill 经验沉淀和动态匹配。
4. HarnessKit 的合法可复用能力优先集成，不重复建设同类扫描系统。
5. 不以侵入式监听换取“完整捕获”；只对用户提供的 Context、导出记录或日志做尽力提取。
6. 核心展示对象是 Skill Flow，不是耗时榜或扫描列表。
7. 工程、安全、合规、测试、兼容性和维护等有标准答案的问题直接解决，不升级为产品决策。
8. 只有产品定位、目标用户、功能范围、体验取舍、优先级冲突或共识变化才交由产品负责人决策。

## 两位成员如何分工

责任可以按工作批次互换，但每个工作项必须有一位唯一负责人和一位复核人。

### 成员 A：基座负责人

主要贡献方向：

- 把已确认的产品目标拆成可交付批次；
- 维护 CLI、数据契约、HarnessKit 适配边界和发布质量；
- 处理可靠性、安全、供应链、许可证、兼容性和自动化测试；
- 为每项实现补齐设计依据、验证结果和变更记录；
- 提供可供成员 B 直接试用的命令、样本和验收说明。

当前优先工作：

1. provider 状态与结构化诊断；
2. 最后成功扫描快照和新鲜度标记；
3. 安装恢复、版本保留、回滚与许可证落盘；
4. 跨平台验证；
5. Harvest 数据模型和 CLI 入口的首版实现。

### 成员 B：体验验证负责人

主要贡献方向：

- 在真实开发流程中使用 NodeHarvest，而不只阅读设计文档；
- 记录首次安装、诊断、扫描、故障恢复和结果理解上的阻力；
- 提供 2–3 个已结束项目的 Context、聊天导出或日志作为 Harvest 验证样本；
- 检查 Skill Flow 能否清楚回答“做了什么、用了什么、为什么、结果如何、留下什么经验”；
- 对候选 Skill 的推荐理由和历史证据做可理解性验证；
- 将发现的问题写成可复现、可验收的工作项。

当前优先工作：

1. 使用发布候选版本完成首次诊断与扫描；
2. 模拟断网、旧快照和 provider 不可用场景，确认提示是否可行动；
3. 准备真实历史项目材料并删除不应共享的敏感信息；
4. 对最小 Skill Flow 样本做人工修订，记录修订成本；
5. 验证推荐结果是否能帮助 Agent 做决定，而不是只返回能力列表。

## 一项贡献如何推进

### 1. 说明问题

工作项至少写清：

- 用户在什么情况下遇到问题；
- 当前行为是什么；
- 期望用户结果是什么；
- 如何复现或提供证据；
- 怎样算完成。

普通工程缺陷不需要等待产品负责人确认。若问题会改变产品范围或既有共识，则标为“产品决策”，暂停实现并提交选择题。

### 2. 认领与复核

- 一项工作只设一位负责人，避免双写和责任模糊；
- 另一位成员默认担任复核人；
- 开始工作前同步远端分支，确认没有重复工作；
- 工作较大时拆成能独立验证的小批次，不建立长期失控分支。

### 3. 实现与记录

一次贡献应尽量同时包含：

- 实现或文档变更；
- 自动化测试或可复现的人工验证；
- 用户可感知行为说明；
- 重要设计、研究和限制的仓库记录；
- 必要的公开文档更新。

不得只在聊天中形成结论。重要决策、研究证据、执行计划、验证结果和已知限制都必须进入组织仓库并提交。

### 4. 提交复核

复核人重点检查：

1. 是否符合 Scan → Harvest → Invoke 的产品主线；
2. 是否把基础设施细节错误包装成新产品功能；
3. 失败时是否给出可信状态，不把旧数据伪装成新数据；
4. 是否有敏感信息、许可证或供应链风险；
5. 是否有测试证据，且文档与实际行为一致；
6. 用户是否能理解并完成下一步操作。

### 5. 合并与同步

- 提交信息说明一项完整意图；
- 推送后核对远端提交；
- 达到批次验收条件后再标记完成；
- 面向用户的状态变化同步到公开文档；
- 未验证的平台和功能明确标为“待验证”，不能描述为已完成。

## 分支与提交约定

建议使用短生命周期分支：

- `feat/<用户能力>`：新增产品能力；
- `fix/<问题>`：修复可复现问题；
- `docs/<主题>`：只更新文档；
- `test/<范围>`：补充测试与验证设施。

提交信息使用清晰的单一意图，例如：

- `feat: 为扫描结果增加过期降级状态`
- `fix: 避免损坏 provider 覆盖已验证版本`
- `docs: 记录 Skill Flow 真实样本验证结果`
- `test: 覆盖 Windows provider 替换行为`

每次提交前至少执行项目构建、自动化测试和与本次行为有关的人工验证。不要提交访问密钥、用户原始私密 Context、构建缓存或无关生成物。

## 双人交接模板

```markdown
## 用户结果
用户现在可以……

## 变更范围
- ……

## 验证证据
- 自动化：……
- 人工：……

## 已知限制
- ……

## 请重点复核
- ……
```

复核反馈必须指向具体用户结果、复现步骤或验收条件，避免只给“感觉不对”或纯偏好意见。

## 当前执行顺序

| 批次 | 成员 A | 成员 B | 完成信号 |
|---|---|---|---|
| 可靠诊断与安全降级 | 实现状态、结构化错误、诊断、快照和新鲜度 | 验证正常、断网、provider 不可用和旧快照体验 | 用户始终知道结果是最新、过期还是不可用 |
| 安装恢复与跨平台 | 实现安装锁、失败清理、版本保留、回滚和许可证落盘 | 在可用平台完成真实首次使用与失败反馈 | 安装失败不破坏可用版本，支持范围有真实证据 |
| 最小 Skill Flow | 实现三类节点、关系、Markdown 与 JSON Schema | 提供真实样本并执行人工修订 | 低成本回答任务、Skill、原因、结果和经验 |
| 动态匹配闭环 | 实现任务查询、候选排序、理由和结果回流 | 检查推荐是否可理解、可采用 | 完成“任务 → 推荐 → 使用 → 结果 → 新经验”演示 |

## 何时需要产品负责人

以下情况才暂停并请求产品决策：

- 要改变 NodeHarvest 的定位、目标用户或 CLI 产品形态；
- 要新增或删除一项用户功能，且会改变 MVP 范围；
- 两种方案代表明显不同的用户体验或价值取舍；
- 真实样本证明最小经验模型或动态匹配假设不成立；
- 要改变开源边界或作出不可逆的生态承诺。

除此之外，两位成员直接按标准工程方案解决、验证、记录并推进，不把执行责任转回产品负责人。
